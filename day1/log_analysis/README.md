# log-analyze

10 万行 nginx 访问日志的流式统计工具，已容器化。

## 统计维度

- 请求数 Top 10 IP
- 状态码分布（条数 + 占比）
- 5xx 总占比，超过 1% 告警
- QPS 峰值（按分钟聚合，定位到具体哪一分钟）

## 运行

本机：

```bash
python log_analyze.py access.log
```

容器：

```bash
docker build -t log-analyze:1.2 .
docker run --rm -v "C:\path\to\access.log:/app/access.log" log-analyze:1.2
```

## 结构

```
read_data(path)   生成器，逐行 split，一次切完存 parts
      ↓
collect(rows)     单次遍历，同时更新 3 个 Counter 和 5xx 计数
      ↓
main()            只负责格式化输出，不再碰文件
```

四个指标必须一轮算完：生成器只能遍历一次，第二次就是空的。这也是函数边界从「谁去读文件」改成「谁去排版」的原因。

## 实测数据

| 版本 | 数据量 | 峰值内存 | 常驻 |
|---|---|---|---|
| 列表版（全量读入） | 10 万行 / 7.7MB | 25.91 MB | 26 MB |
| 流式版 | 10 万行 / 7.7MB | 6.99 MB | 567 KB |
| 流式版 | 40 万行 / 30.7MB | 0.55 MB | 7.1 MB |

数据量翻 4 倍，峰值不增——流式的意义在于内存与数据量解耦，不是「写法优雅」。

## 设计取舍

**日志不进镜像。** 代码进镜像、数据靠挂载，否则日志一变就要重新 build 一个 177MB 的镜像。`.dockerignore` 同时让构建上下文从 7.7MB 降到 1.9KB。

**入口接受路径参数。** `sys.argv[1]` 指定文件，不传则默认 `access.log`，本机与容器共用同一份代码。

**文件不存在时 `sys.exit` 而非 `print`。** 退出码必须是 1，容器编排靠退出码判断是否异常终止。

**split 只做一次。** 判断字段数和产出共用同一个 `parts`，避免每行切两遍（实测快 46%）。

## 待改进

- 状态码用 `parts[-2]` 提取，依赖日志字段数固定为 9；换成带 UA 的 nginx combined 格式会取错位置，应改为正则匹配
- 未处理超长行、编码异常等真实日志的脏数据
